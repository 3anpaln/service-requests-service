# Service Requests Service

A .NET 10 Minimal API for creating service requests, tracking status changes, and publishing events through RabbitMQ. EF Core persists requests and messaging records in PostgreSQL.

## Run

Install Docker with Compose v2; install the .NET 10 SDK for tests. From the repository root, enter the nested solution directory and start the application (PowerShell):

```powershell
Set-Location .\service-requests-service
if (!(Test-Path .env)) { Copy-Item .env.example .env }
# Set POSTGRES_* and RABBITMQ_USER/RABBITMQ_PASSWORD values in .env.
docker compose up --build -d
```

Compose starts PostgreSQL, RabbitMQ, and the API; EF Core migrations run automatically at startup. Check startup logs with `docker compose logs -f webapi`. Once ready, verify `http://localhost:8080/health`, for example with `Invoke-RestMethod`. RabbitMQ management is at `http://localhost:15672`, using the configured credentials. Stop with `docker compose down`; named volumes retain database and broker data. Compose supplies the API's database connection and RabbitMQ host settings through environment variables.

Endpoints: `POST /api/service-requests`, `GET /api/service-requests`, `GET /api/service-requests/{id}`, and `PATCH /api/service-requests/{id}/status`. Example POST body: `{"title":"Restore service","priority":3}`. PATCH accepts a bare number, such as `2` for InProgress. Priorities: Low=1, Normal=2, High=3; statuses: New=1, InProgress=2, Done=3, Cancelled=4.

## Test

From the same solution directory:

```powershell
dotnet test tests/service-requests-service.UnitTests/service-requests-service.UnitTests.csproj --configuration Release
```

Target the project explicitly: it is not currently registered in `service-requests-service.sln`. The 26 xUnit `[Fact]` tests cover creation, status transitions, invalid statuses, missing requests, cancellation, outbox contents, and transactional rollback. Moq replaces the outbox dependency and logger; SQLite in memory exercises EF Core transactions without Docker, PostgreSQL, or RabbitMQ. PostgreSQL-specific behavior and broker delivery require integration tests.

## Decisions and assumptions

- Minimal API endpoints and scoped EF Core services keep the implementation small. FluentValidation checks creation input, and exception handling uses Problem Details.
- Request mutations and outbox events share one transaction. A worker attempts publication immediately and every 60 seconds; downstream processing is asynchronous. Events carry idempotency keys to support duplicate detection.
- New requests default to Normal priority. Allowed transitions are New to InProgress/Cancelled, InProgress to Done/Cancelled, and Cancelled to New; Done is terminal. Forbidden transitions return HTTP 409.
- IDs are generated by the application and creation times use UTC. The current scope assumes a trusted development environment and one application instance.
